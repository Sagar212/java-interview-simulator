1) VOLATILE KEYWORD
============================================================

Constraint -> Pattern
If the interview question is about visibility between threads, instruction ordering, or a simple shared flag, think: volatile. If the question is about compound operations like count++, think: volatile is not enough.

Core Interview Answer
volatile guarantees visibility and ordering for reads and writes of a variable across threads, but it does not guarantee atomicity for compound operations. A write to a volatile variable by one thread becomes visible to another thread reading that same variable, and the JVM also prevents certain instruction reordering around volatile accesses.

What guarantees does volatile provide regarding visibility and ordering?
- Visibility: when one thread updates a volatile variable, other threads see the latest value instead of a stale cached value.
- Ordering: volatile establishes a happens-before relationship. A write to a volatile variable happens-before every subsequent read of that variable by another thread.
- Reordering protection: the JVM inserts memory barriers so certain reads/writes cannot be reordered across volatile boundaries.

How does volatile differ from synchronized?
- volatile gives visibility and ordering only for a single variable.
- synchronized gives mutual exclusion, visibility, and ordering.
- volatile does not lock.
- synchronized prevents two threads from executing a critical section at the same time.
- volatile is usually lighter but weaker.

Can volatile ensure atomicity? Why or why not?
No. Atomicity means the whole operation happens as one indivisible unit. count++ is actually three steps:
1. Read count
2. Add 1
3. Write count
Even if count is volatile, two threads can still interleave these steps and lose updates.

When is volatile unnecessary in multithreading?
- When the variable is accessed only inside synchronized blocks or locks.
- When the variable is thread-confined.
- When you need atomicity, use synchronized, Lock, or atomic classes instead.
- When the field is final and safely published, volatile may not be needed.

Java Template
class SharedFlag {
    // visible to all threads immediately
    private volatile boolean running = true;

    public void stop() {
        running = false;
    }

    public void work() {
        while (running) {
            // do work
        }
    }
}

Memory Recall Table
- volatile -> visibility yes
- volatile -> ordering yes
- volatile -> atomicity no
- synchronized -> visibility yes
- synchronized -> ordering yes
- synchronized -> atomicity yes inside critical section

Why It Works + Memory Pointer
Think of volatile like updating a shared office whiteboard instead of writing on your own sticky note. Every thread must read the whiteboard, but volatile does not stop two people from writing over each other at the same time.

Pain Points + Java Pitfalls
- Biggest trap: saying volatile makes code thread-safe. It does not.
- volatile works well for status flags, shutdown signals, configuration refresh markers.
- It is not enough for increment/decrement, check-then-act, read-modify-write logic.

Follow-up Drills
- Why does volatile work for boolean stop flags?
- Why does volatile fail for count++?
- Compare AtomicInteger vs volatile int.

2) STATIC KEYWORD
============================================================

Constraint -> Pattern
If the question is about class-level data or behavior shared by all objects, think static.

Core Interview Answer
static members belong to the class, not to individual objects. They are loaded once per class loader, shared across all instances, and can be accessed without creating an object.

How do static variables behave in multithreading?
- static means shared per class, not thread-safe.
- If multiple threads update a static field, race conditions can happen just like with any shared instance field.
- static + mutable is a common concurrency bug source.

Difference between static block and static method?
- static block runs automatically when the class is initialized.
- static method runs only when called.
- static block is mostly used for class-level initialization.
- static method contains reusable class-level behavior.

Can static methods participate in polymorphism?
Not true runtime polymorphism. Static methods are resolved at compile time based on reference type, not object type.

What is method hiding vs overriding for static methods?
- Instance methods are overridden.
- Static methods are hidden.
- If a subclass defines a static method with the same signature, it hides the parent static method rather than overriding it.

Java Template
class Parent {
    static void show() {
        System.out.println("Parent");
    }
}

class Child extends Parent {
    static void show() {
        System.out.println("Child");
    }
}

Memory Recall Table
- static variable -> one copy per class loader
- static method -> class-level behavior
- static block -> class initialization
- static method polymorphism -> no runtime overriding

Why It Works + Memory Pointer
Think of static as a notice board mounted on the building, not inside each apartment. Everyone in that building sees the same board.

Pain Points + Java Pitfalls
- static does not mean thread-safe.
- static methods cannot directly access instance fields because no object context exists.
- Avoid mutable static state in Spring apps unless carefully managed.

Follow-up Drills
- Difference between static final and static mutable.
- Why is utility class method usually static?
- Why can static methods not use this?

3) FUNCTIONAL INTERFACE
============================================================

Constraint -> Pattern
If the question mentions lambda, method reference, or Java 8 single abstract method, think functional interface.

Core Interview Answer
A functional interface is an interface with exactly one abstract method. It may still have multiple default and static methods because those do not count as abstract methods.

How do default and static methods allow multiple methods?
- Because the functional-interface rule counts only abstract methods.
- default methods already have implementation.
- static methods belong to the interface type and also do not count toward abstract method count.

What happens if more than one abstract method exists?
Then it is no longer a functional interface, so lambdas cannot target it.

Can it extend another interface and still remain functional?
Yes, if after inheritance there is still exactly one abstract method in total.

How do lambdas depend on functional interfaces?
A lambda expression needs a target type, and that target type is usually a functional interface. The lambda provides implementation for the single abstract method.

Java Template
@FunctionalInterface
interface Calculator {
    int apply(int left, int right);

    default void log() {
        System.out.println("running");
    }

    static void info() {
        System.out.println("functional interface");
    }
}

class Demo {
    public static void main(String[] args) {
        Calculator add = (left, right) -> left + right;
        System.out.println(add.apply(2, 3));
    }
}

Memory Recall Table
- one abstract method -> yes functional
- default method -> allowed
- static method -> allowed
- second abstract method -> lambda breaks

Why It Works + Memory Pointer
Imagine hiring one person for one job role. They may have handbook instructions and company-wide rules, but only one core responsibility defines the role.

Pain Points + Java Pitfalls
- Object class methods like toString do not count as extra abstract methods.
- @FunctionalInterface is optional but recommended because compiler validates the contract.

Follow-up Drills
- Predicate, Function, Consumer, Supplier differences.
- Lambda vs method reference.
- Can private methods exist in interfaces? Yes in newer Java versions.

4) GARBAGE COLLECTION
============================================================

Constraint -> Pattern
If the question is about memory cleanup, unreachable objects, or GC tuning, think reachability + generations + collector strategy.

Core Interview Answer
The JVM garbage collector automatically reclaims heap memory occupied by objects that are no longer reachable from live references. Modern collectors optimize for pause time, throughput, and memory footprint using generational memory management.

How does JVM identify objects for GC?
- It starts from GC roots: stack references, static references, active threads, JNI references.
- Objects reachable from these roots are considered alive.
- Unreachable objects become eligible for collection.

Minor vs Major vs Full GC differences?
- Minor GC: collects young generation.
- Major GC: usually collects old generation.
- Full GC: collects entire heap, often including young + old and sometimes metaspace-related cleanup depending on JVM behavior.

How do G1, CMS, Serial GC differ?
- Serial GC: one thread, simple, good for small heaps.
- CMS: low-pause old-gen collector, largely deprecated in modern Java.
- G1: region-based collector designed for predictable pause times and large heaps.

How to monitor and tune GC?
- Enable GC logs.
- Watch pause times, allocation rate, old-gen pressure, promotion failures.
- Tune heap sizes, region sizes, pause goals, collector choice.
- Use tools like jstat, jcmd, VisualVM, JMC, Micrometer exporters, APM tools.

Memory Recall Table
- reachability -> GC basis
- young gen -> minor GC
- old gen -> major GC
- whole heap -> full GC
- low pause modern default -> G1 in many setups

Why It Works + Memory Pointer
Think of memory like a hotel. GC checks which rooms are still connected to active guest records. Unregistered rooms get cleaned and reused.

Pain Points + Java Pitfalls
- finalize is obsolete and unreliable for core interview answers.
- System.gc() is only a request, not a guarantee.
- Memory leak in Java still happens when references remain reachable accidentally.

Follow-up Drills
- Strong vs weak vs soft vs phantom references.
- Why do short-lived objects make generational GC efficient?
- What causes stop-the-world pauses?

5) SPRING BOOT LIFECYCLE
============================================================

Constraint -> Pattern
If the question is about startup sequence, bean creation, hooks, or runners, think SpringApplication -> context creation -> bean initialization -> post-start hooks.

Core Interview Answer
During Spring Boot startup, SpringApplication bootstraps the app, creates and refreshes the ApplicationContext, registers beans, performs dependency injection, runs initialization callbacks, and then invokes startup runners such as CommandLineRunner or ApplicationRunner.

What happens during application startup?
1. main method calls SpringApplication.run(...)
2. Spring creates the Environment.
3. ApplicationContext is created.
4. Bean definitions are loaded.
5. Beans are instantiated.
6. Dependencies are injected.
7. Bean lifecycle callbacks run.
8. Application runners execute.
9. Ready events are published.

How are beans created and injected?
- Component scanning or @Bean methods define beans.
- Spring resolves dependencies from the context.
- Constructor injection is preferred.
- BeanPostProcessor and lifecycle callbacks can modify beans before/after initialization.

How to hook into lifecycle events?
- @PostConstruct
- InitializingBean
- BeanPostProcessor
- ApplicationListener
- @EventListener for events like ApplicationStartedEvent or ApplicationReadyEvent

ApplicationRunner vs CommandLineRunner?
- Both run after context startup.
- CommandLineRunner gets String[] args.
- ApplicationRunner gets ApplicationArguments, which is richer and easier for option parsing.

Java Template
@Component
class StartupTask implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        System.out.println("App started");
    }
}

Memory Recall Table
- SpringApplication.run -> bootstrap entry
- ApplicationContext -> bean container
- @PostConstruct -> bean init hook
- CommandLineRunner -> String[] args
- ApplicationRunner -> parsed args wrapper

Why It Works + Memory Pointer
Think of Spring Boot startup like opening a factory: prepare environment, assemble machines, wire them together, test them, then start production tasks.

Pain Points + Java Pitfalls
- Do not put heavy blocking startup work everywhere; it can slow boot time.
- Prefer constructor injection over field injection.
- Know the difference between bean initialization and app-ready events.

Follow-up Drills
- @PostConstruct vs ApplicationReadyEvent.
- Bean scope differences.
- What happens on shutdown? @PreDestroy and lifecycle stop.

6) SERIALIZATION
============================================================

Constraint -> Pattern
If the question is about converting object state into bytes and back, think Serializable + object stream + compatibility.

Core Interview Answer
Serialization is the process of converting an object's state into a byte stream so it can be stored or transmitted, and deserialization reconstructs the object from that byte stream. In Java, this typically uses the Serializable marker interface and ObjectOutputStream/ObjectInputStream.

How does Serializable work internally?
- Serializable is a marker interface with no methods.
- JVM/Object stream checks whether a class implements it.
- Non-transient, non-static fields are serialized by default.
- During deserialization, object state is reconstructed without calling normal constructors in the usual way for serializable classes.

What is serialVersionUID?
- It is a version identifier for a serializable class.
- During deserialization, JVM compares stream class version with local class version.
- If incompatible and serialVersionUID differs, InvalidClassException may occur.

How do readObject/writeObject customize behavior?
- private void writeObject(ObjectOutputStream out)
- private void readObject(ObjectInputStream in)
These hooks let you customize serialization logic, validate data, encrypt/decrypt fields, or rebuild derived fields.

What happens when class structure changes?
- Compatible changes may still deserialize.
- Incompatible changes can fail, especially if serialVersionUID changes or important fields disappear/change type.
- Explicit serialVersionUID gives you more control.

Java Template
class UserSession implements java.io.Serializable {
    private static final long serialVersionUID = 1L;

    private String username;
    private transient String password;
}

Memory Recall Table
- Serializable -> marker interface
- transient -> skip field
- static -> not serialized
- serialVersionUID -> version contract
- readObject/writeObject -> custom logic

Why It Works + Memory Pointer
Think of serialization like packing an object's suitcase for transport. transient fields are items you intentionally leave behind.

Pain Points + Java Pitfalls
- Do not use Java native serialization blindly in distributed systems; security and compatibility concerns exist.
- transient is often forgotten.
- serialVersionUID should be explicit for stable contracts.

Follow-up Drills
- transient vs static in serialization.
- Why is native Java serialization often avoided in modern APIs?
- Externalizable vs Serializable.

7) RUNNABLE VS CALLABLE
============================================================

Constraint -> Pattern
If the task needs background execution only, Runnable may be enough. If it needs a return value or checked exception handling, think Callable.

Core Interview Answer
Runnable represents a task that does not return a result, while Callable represents a task that returns a result and may throw checked exceptions. Callable is usually submitted to ExecutorService and returns a Future.

Difference between Runnable and Callable?
- Runnable -> run(), returns void, cannot throw checked exception.
- Callable<V> -> call(), returns V, can throw checked exception.

When should you use Callable over Runnable?
- When you need a result.
- When you want checked exception propagation.
- When the task is naturally query-like instead of fire-and-forget.

What is Future and how does it work?
- Future represents the result of an asynchronous computation.
- You can check isDone(), cancel(), or get() the result.
- get() blocks until completion unless using timeout.

How does ExecutorService manage threads?
- It decouples task submission from thread management.
- It reuses threads through pools.
- It improves scalability compared to creating raw threads manually.

Java Template
ExecutorService service = Executors.newFixedThreadPool(2);
Callable<Integer> task = () -> 42;
Future<Integer> future = service.submit(task);
int result = future.get();
service.shutdown();

Memory Recall Table
- Runnable -> no result
- Callable -> result + checked exception
- Future -> async handle
- ExecutorService -> thread pool manager

Why It Works + Memory Pointer
Think of Runnable as giving someone a chore. Callable is giving them a task and expecting a report back.

Pain Points + Java Pitfalls
- Forgetting shutdown() causes thread pool leaks.
- future.get() blocks; it is not magically non-blocking.
- Prefer executors over manual thread creation in most production cases.

Follow-up Drills
- submit() vs execute().
- Future vs CompletableFuture.
- Fixed thread pool vs cached thread pool.

8) @QUALIFIER ANNOTATION
============================================================

Constraint -> Pattern
If Spring finds multiple candidate beans of the same type and injection becomes ambiguous, think @Qualifier.

Core Interview Answer
@Qualifier is used in Spring to specify exactly which bean should be injected when multiple beans of the same type exist. It resolves ambiguity during dependency injection.

Why is @Qualifier needed?
Because type-based autowiring alone fails when more than one matching bean exists.

How does it resolve ambiguity in Spring?
It narrows the candidate bean set by bean name or qualifier value.

Difference between @Primary and @Qualifier?
- @Primary marks a default bean when multiple candidates exist.
- @Qualifier explicitly selects a bean.
- @Qualifier is stronger and more specific at injection point.

Can you use it with constructor injection?
Yes, and that is a common best practice.

Java Template
@Service("emailService")
class EmailService implements MessageService {}

@Service("smsService")
class SmsService implements MessageService {}

@Component
class NotificationManager {
    private final MessageService messageService;

    public NotificationManager(@Qualifier("emailService") MessageService messageService) {
        this.messageService = messageService;
    }
}

Memory Recall Table
- multiple beans same type -> ambiguity
- @Primary -> default winner
- @Qualifier -> exact winner
- constructor injection -> preferred

Why It Works + Memory Pointer
Think of @Primary as the default contact in your phone, while @Qualifier is choosing a specific contact by name.

Pain Points + Java Pitfalls
- Bean name mismatch causes injection errors.
- Overusing qualifiers everywhere can make config noisy.
- Prefer clear bean design before piling on qualifiers.

Follow-up Drills
- @Resource vs @Autowired + @Qualifier.
- Collection injection of all beans of same type.
- Custom qualifier annotations.

9) INTERFACE VS ABSTRACT CLASS (JAVA 8+)
============================================================

Constraint -> Pattern
If the interview asks shared contract vs shared state/partial implementation, compare interface and abstract class.

Core Interview Answer
After Java 8, interfaces can contain default and static methods, but they still mainly represent a contract, while abstract classes are better for shared state, constructors, and partial base implementation.

What differences still exist after default methods?
- Abstract class can have instance state.
- Abstract class can have constructors.
- A class can extend only one abstract class.
- A class can implement multiple interfaces.
- Interfaces are still more flexible for multiple inheritance of type.

When should you prefer abstract class?
- When subclasses share common state.
- When base constructor logic is needed.
- When you want to provide protected helper methods and partial implementation.

Multiple inheritance via interfaces vs abstract class?
- Java allows multiple interface implementation.
- Java does not allow multiple class inheritance.

State management differences?
- Interface fields are implicitly public static final constants.
- Abstract classes can hold mutable instance fields.

Memory Recall Table
- interface -> contract
- abstract class -> contract + state + partial implementation
- multiple inheritance -> interfaces yes, classes no

Why It Works + Memory Pointer
Interface is like a job description. Abstract class is like a partially built machine with reusable internal parts.

Pain Points + Java Pitfalls
- Do not say interfaces fully replace abstract classes after Java 8.
- Default methods help evolution but do not make interfaces ideal for shared mutable state.

Follow-up Drills
- Diamond problem with default methods.
- Marker interface vs annotation.
- Sealed interfaces/classes in modern Java.

10) OOP CONCEPTS
============================================================

Constraint -> Pattern
If asked OOP basics, answer with definition + Java implementation + real-world example.

Core Interview Answer
Encapsulation bundles data and methods together while restricting direct access, abstraction hides internal complexity and shows only essential behavior, and polymorphism lets the same interface behave differently based on the actual implementation.

Real-world examples of each?
- Encapsulation: BankAccount hides balance updates behind deposit/withdraw methods.
- Abstraction: Car driver uses steering/brake without knowing engine internals.
- Polymorphism: PaymentService can process CardPayment, UpiPayment, or WalletPayment through common interface.

Compile-time vs runtime polymorphism?
- Compile-time polymorphism -> method overloading.
- Runtime polymorphism -> method overriding resolved by actual object type.

How does abstraction differ from encapsulation?
- Abstraction focuses on what to expose.
- Encapsulation focuses on how to protect internal state.

How are these implemented in Java?
- Encapsulation -> private fields + getters/setters/behavior methods.
- Abstraction -> interfaces and abstract classes.
- Polymorphism -> overriding and interface-based programming.

Memory Recall Table
- encapsulation -> protect state
- abstraction -> hide complexity
- polymorphism -> one contract, many behaviors

Why It Works + Memory Pointer
Encapsulation is a capsule. Abstraction is a dashboard. Polymorphism is one remote controlling different devices.

Pain Points + Java Pitfalls
- Students often mix abstraction and encapsulation.
- Overusing getters/setters without real invariants is weak encapsulation.

Follow-up Drills
- Inheritance vs composition.
- Why favor composition over inheritance?
- Is method overloading truly polymorphism? Interviewers may call it compile-time polymorphism.

11) METHOD OVERLOADING VS OVERRIDING
============================================================

Core Interview Answer
Overloading means same method name with different parameter lists in the same class or hierarchy, resolved at compile time. Overriding means subclass provides a new implementation of an inherited instance method with same signature, resolved at runtime.

Key differences?
- Overloading -> compile-time binding.
- Overriding -> runtime binding.
- Overloading changes parameters.
- Overriding keeps same signature, compatible return type.

Rules for overriding?
- Same method signature.
- Return type same or covariant.
- Access cannot be more restrictive.
- Checked exceptions cannot be broader than parent declaration.
- final/private methods cannot be overridden.

Can static methods be overridden?
No. They are hidden, not overridden.

How does compile-time vs runtime binding work?
- Compiler decides overloaded method based on reference type and argument list.
- JVM chooses overridden instance method based on actual object type.

Memory Recall Table
- overload -> same name, different params
- override -> same signature, new child logic
- static -> hiding, not overriding

Why It Works + Memory Pointer
Overloading is choosing a tool shape before work starts. Overriding is same button label doing different work depending on which machine you are using.

Pain Points + Java Pitfalls
- Changing only return type does not overload.
- private methods are not overridden.

Follow-up Drills
- Can you overload main? Yes.
- Can constructors be overridden? No.
- What is bridge method? Advanced generic topic.

12) METHOD HIDING
============================================================

Core Interview Answer
Method hiding happens when a subclass defines a static method with the same signature as a static method in the parent class. The method called depends on the reference type, not the actual object type.

Difference between hiding and overriding?
- Hiding applies to static methods.
- Overriding applies to instance methods.
- Hiding uses compile-time binding.
- Overriding uses runtime dispatch.

How does static binding work?
The compiler binds the static method call to the declared reference type.

When is method hiding used?
Usually not as a design goal. It appears when subclasses define same-named utility or factory-like static methods.

Example
Parent ref = new Child();
ref.show(); // Parent.show if show is static

Memory Recall Table
- static + same signature -> hiding
- instance + same signature -> overriding
- reference type decides hidden method

Why It Works + Memory Pointer
Static methods belong to the class label on the box, not the object inside the box.

Pain Points + Java Pitfalls
- Many candidates incorrectly say static methods override.
- Using object reference to call static methods is legal but poor style.

13) COVARIANT RETURN TYPE
============================================================

Core Interview Answer
Covariant return type means an overriding method in a subclass can return a more specific type than the method declared in the parent class.

What is it and why is it useful?
It improves type safety and reduces casting for callers.

Rules for covariant return types?
- Same method signature.
- Child return type must be a subtype of parent return type.
- Applies to overriding, not arbitrary overload changes.

How does it help in method overriding?
The subclass can return a richer, more specific object while still honoring parent contract.

Real-world use cases?
- Factory methods.
- Fluent APIs.
- Clone/copy methods in inheritance hierarchies.

Example
class Animal {}
class Dog extends Animal {}

class Parent {
    Animal getPet() { return new Animal(); }
}

class Child extends Parent {
    @Override
    Dog getPet() { return new Dog(); }
}

Memory Recall Table
- parent returns broad type
- child may return narrower subtype
- safer API, fewer casts

14) CLASS WITHOUT MAIN METHOD
============================================================

Core Interview Answer
A normal standalone Java application requires a valid main method as JVM entry point. However, code can still execute without writing your own main when a framework, test runner, servlet container, or launcher provides the entry point.

Can Java run without main method?
- Standalone class directly with java command: needs main.
- Framework-driven execution: your business class may not need its own main.

How do frameworks like Spring Boot run apps?
Spring Boot apps still usually have a main method that calls SpringApplication.run. After that, Spring manages the lifecycle and execution flow.

What is the actual JVM entry point?
public static void main(String[] args)

Can static blocks execute without main?
Static blocks run when class loads, but for a standard application some entry mechanism still has to trigger class loading. In very old interview tricks, people used static blocks with older JVM behavior, but modern Java requires proper entry structure for direct execution.

Memory Recall Table
- JVM app entry -> main
- framework hides flow, not JVM rule
- static block != official app entry

15) ANONYMOUS CLASS
============================================================

Core Interview Answer
An anonymous class is a one-time class declaration and instantiation written inline, typically used when a short custom implementation is needed without creating a separate named class.

When should you use it?
- Small one-off implementations.
- Event handlers.
- Temporary interface or abstract-class implementations.
- Less common now when lambdas fit better.

Anonymous class vs lambda?
- Anonymous class creates an actual class body.
- Lambda is a compact function-like implementation for functional interfaces.
- Anonymous class can define extra fields/methods.
- Lambda is cleaner for single abstract method behavior.

Limitations of anonymous classes?
- Cannot have explicit constructors.
- Harder to read when large.
- Cannot be reused by name.
- this refers to anonymous class instance, unlike lambda where this refers to enclosing instance.

Example
Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println("running");
    }
};

Memory Recall Table
- one-off implementation -> anonymous class
- SAM compact behavior -> lambda
- big body -> readability drops

16) HASHMAP INTERNAL WORKING
============================================================

Constraint -> Pattern
If the interview asks storage, collisions, hashing, Java 8 treeification, think array + bucket + node chain/tree.

Core Interview Answer
HashMap stores key-value pairs in an internal array of buckets. It uses a key's hash to compute bucket index, stores entries as nodes, handles collisions by placing multiple entries in the same bucket, and in Java 8 can convert heavily-collided buckets from linked list form to a balanced tree for better worst-case lookup.

How does HashMap store data?
- Internal array called table.
- Each bucket holds nodes.
- Node stores hash, key, value, next.
- Index derived from processed hash and table size.

How are collisions handled?
- Multiple keys may map to same bucket.
- Bucket entries are traversed by equals comparison after hash matching.
- Historically linked list, Java 8 may treeify under heavy collision.

What changed in Java 8 (treeification)?
- Long collision chains can become red-black trees.
- This improves worst-case bucket lookup from O(n) to O(log n).
- Treeification happens only beyond threshold and sufficient capacity.

Difference from ConcurrentHashMap?
- HashMap is not thread-safe.
- ConcurrentHashMap supports concurrent access with finer-grained synchronization/CAS strategies.
- ConcurrentHashMap disallows null keys and null values; HashMap allows one null key and multiple null values.

Memory Recall Table
- hashCode -> bucket index
- equals -> exact key match
- collision -> chain/tree in bucket
- Java 8 -> treeification
- HashMap -> not thread-safe

Why It Works + Memory Pointer
Think of HashMap as apartment buildings (buckets). hashCode picks the building, equals finds the exact flat.

Pain Points + Java Pitfalls
- Equal objects must have equal hashCode.
- Mutable keys are dangerous.
- Worst interview mistake: saying HashMap is always O(1) with no caveat.

Follow-up Drills
- Why are immutable keys preferred?
- What triggers resize?
- Why capacity often power of two?

17) DESIGN PATTERNS
============================================================

Core Interview Answer
Design patterns are reusable, proven solution templates for recurring software design problems. They are broadly grouped into creational, structural, and behavioral patterns.

What are creational, structural, behavioral patterns?
- Creational -> object creation (Singleton, Factory, Builder).
- Structural -> class/object composition (Adapter, Decorator, Facade).
- Behavioral -> object interaction/responsibility flow (Strategy, Observer, Command).

Singleton pitfalls in multithreading?
- Lazy singleton without synchronization can create multiple instances.
- Double-checked locking requires volatile.
- Overuse of singleton can harm testability and design.

Factory vs Abstract Factory?
- Factory Method usually creates one product type through inheritance or overridden creation.
- Abstract Factory creates families of related objects.

When to use Builder pattern?
- Many optional parameters.
- Immutable object construction.
- Better readability than telescoping constructors.

Scenario-based design patterns
- Object creation flexibility -> Factory / Builder / Abstract Factory.
- Decoupling systems -> Observer / Adapter / Facade / Dependency Injection.
- Dynamic behavior changes -> Strategy / State / Decorator.
- How to choose right pattern? Start from problem: creation, structure, or behavior. Do not force patterns unnecessarily.

Memory Recall Table
- create -> creational
- connect -> structural
- communicate/change behavior -> behavioral

Why It Works + Memory Pointer
Patterns are like standard machine blueprints. You do not reinvent the engine mount every time.

Pain Points + Java Pitfalls
- Pattern names without problem context sound memorized.
- Explain trade-off, not just definition.

18) STRING == VS EQUALS
============================================================

Core Interview Answer
For Strings, == compares references, while equals() compares character content. Two different String objects with same text may be equals() true but == false unless they refer to the same pooled object.

Difference between == and equals?
- == -> same object reference?
- equals -> same logical content?

What is string pool?
It is a special memory area where JVM reuses string literals and interned strings to avoid duplicate objects.

How does interning work?
intern() returns the canonical pooled representation of the string. If equivalent content already exists in pool, it returns that reference; otherwise it adds it to the pool.

Why are Strings immutable?
- Security.
- Hashing stability.
- Pooling support.
- Thread-safety benefits.

Example
String a = "java";
String b = "java";
String c = new String("java");

a == b      // true
a == c      // false
a.equals(c) // true

Memory Recall Table
- == -> address/reference
- equals -> content
- intern -> pooled canonical reference
- immutable -> safe and reusable

19) OVERLOADING MAIN METHOD
============================================================

Core Interview Answer
Yes, main can be overloaded, but JVM calls only the standard signature public static void main(String[] args) as the application entry point.

Can main be overloaded?
Yes, like any static method.

Will JVM call overloaded main?
No, not as startup entry. JVM looks for the exact standard main signature.

Use cases for overloading main?
- Internal testing helpers.
- Teaching/demo code.
- Convenience wrappers called manually from standard main.

What if standard main is missing?
The class cannot start as a normal Java application using java command.

Should you overload main?
Usually avoid it in production code because it hurts readability more than it helps.

Practical use cases?
- Small demo programs.
- Interview explanation.
- Delegating parsing logic from main to helper methods, though separate helper names are usually clearer.

Testing scenarios?
Better use JUnit tests than overloaded main methods.

Readability concerns?
Overloaded main can confuse maintainers about real entry path.

Alternative approaches?
Use helper methods, test classes, or command parser services.

20) THREAD CREATION
============================================================

Constraint -> Pattern
If the question is about creating concurrent execution in Java, think Thread, Runnable, Callable, Executor framework, and lifecycle states.

Core Interview Answer
Threads in Java can be created by extending Thread, implementing Runnable, using Callable with ExecutorService, or using higher-level concurrency abstractions. In modern applications, Executor framework is generally preferred over manual thread creation.

Ways to create threads in Java?
- Extend Thread.
- Implement Runnable.
- Implement Callable and submit to ExecutorService.
- Use thread pools via Executors.
- Use CompletableFuture or parallel abstractions for higher-level async tasks.

Runnable vs Thread class?
- Extending Thread couples task and thread.
- Runnable separates task from execution mechanism.
- Runnable is more flexible because class can still extend something else.

Executor framework benefits?
- Thread reuse.
- Better resource management.
- Queueing and scheduling support.
- Cleaner production-grade concurrency.

Thread lifecycle states?
- NEW
- RUNNABLE
- BLOCKED
- WAITING
- TIMED_WAITING
- TERMINATED

Java Template
class Task implements Runnable {
    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName());
    }
}

public class Demo {
    public static void main(String[] args) {
        Thread thread = new Thread(new Task());
        thread.start();
    }
}

Memory Recall Table
- extend Thread -> simplest demo, less flexible
- Runnable -> preferred basic style
- Callable -> result needed
- ExecutorService -> production style

Why It Works + Memory Pointer
Creating Thread manually is like hiring one worker each time. ExecutorService is like using a managed staffing agency.

Pain Points + Java Pitfalls
- Never call run() directly when you mean concurrent execution; call start().
- Too many raw threads can hurt performance.
- Shared mutable data still needs synchronization even when using executors.

MOCK INTERVIEW MICRO-ANSWERS
============================================================

Q: Why not use volatile for counter?
A: Because increment is read-modify-write, which is not atomic.

Q: Is static thread-safe?
A: No, static only means shared per class, not synchronized.

Q: Can functional interface have many methods?
A: It can have many default/static methods, but only one abstract method.

Q: Why use ApplicationRunner?
A: It gives parsed application arguments and runs after context startup.

Q: Why explicit serialVersionUID?
A: To control compatibility during deserialization.

Q: Why prefer Runnable over extending Thread?
A: Better separation of task from execution and avoids single inheritance limitation.

Q: Why @Qualifier when @Primary exists?
A: @Primary is default preference; @Qualifier selects a specific bean explicitly.

Q: Why abstract class if interfaces have default methods?
A: Abstract classes still support shared state, constructors, and protected reusable logic.

Q: Why are Strings immutable?
A: Security, pooling, stable hashCode, and safer sharing.

Q: Why not raw Thread in production?
A: Poor resource management and no pooling; executors scale better.
